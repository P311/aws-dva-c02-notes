## 1. S3 Overview

### Core Concepts

**Three levels**: AWS account → Bucket (globally unique name, bound to a region) → Object (Key + Value + Metadata + Version ID)

**Key numbers**:

| Trait | Value |
|---|---|
| Single object size | 0 bytes – **50 TB** (raised from 5 TB as of Dec 2, 2025) |
| Single PUT | up to **5 GB**; beyond that requires multipart |
| Recommended multipart threshold | above **100 MB** |
| Bucket limit (per account) | 100 by default, can be raised to 1000 |
| Bucket naming | globally unique, 3-63 characters, lowercase only, no underscores |
| Object key length | up to 1024 bytes |
| Object count | unlimited |
| Durability | **11 nines** (99.999999999%) |
| Availability | 4 nines (Standard) |

> ⚠️ 50 TB only took effect in late 2025 — exam question banks may still show 5 TB. Check the current docs for anything load-bearing.

**Bucket naming rules**: 3-63 characters; lowercase letters, numbers, hyphens (-), dots (.); no underscores; no uppercase; cannot start/end with a hyphen; cannot look like an IP address; cannot start with `xn--`.

**Key concepts**: bucket names are **globally unique**; a bucket is a **region-scoped** resource, with objects physically stored across multiple AZs within that region; there is no "directory" concept — object keys are flat strings; objects are immutable — they can only be overwritten wholesale.

**11 nines of durability**: storing 10 million objects, the expected loss is roughly 1 every 10,000 years.

### Storage Classes ⭐⭐⭐

| Class | Use case | Storage cost | Retrieval cost | Retrieval time | Min. storage duration | Multi-AZ |
|---|---|---|---|---|---|---|
| **Standard** | Frequent access | Standard | None | Instant | None | ✅ Multi-AZ |
| **Standard-IA** | Infrequent access, instant when needed | Cheap | Retrieval fee | Instant | 30 days | ✅ Multi-AZ |
| **One Zone-IA** | Infrequent + regeneratable data | Cheaper | Retrieval fee | Instant | 30 days | ❌ Single AZ |
| **Intelligent-Tiering** | Unpredictable access patterns | Auto-adjusts | None | Instant | None | ✅ Multi-AZ |
| **Glacier Instant Retrieval** | Archive + occasional instant read | Very cheap | Yes | Instant | 90 days | ✅ Multi-AZ |
| **Glacier Flexible Retrieval** | Archive, not urgent | Cheaper | Yes | Minutes to hours | 90 days | ✅ Multi-AZ |
| **Glacier Deep Archive** | Long-term archive | **Cheapest** | Yes | 12+ hours | 180 days | ✅ Multi-AZ |

**The three Glacier retrieval speeds**:

- **Glacier Flexible Retrieval**: Expedited (1-5 min, most expensive), Standard (3-5 hours, default), Bulk (5-12 hours, cheapest)
- **Glacier Deep Archive**: Standard (12 hours), Bulk (48 hours)

**When One Zone-IA fits**: ✅ transcoded video thumbnails (the source video sits in Standard and can regenerate them), ✅ cached ML inference results, ✅ a second copy of a backup. ❌ a user's only original uploaded photo, ❌ compliance audit logs.

**Intelligent-Tiering key points**: **no retrieval fee** regardless of which tier serves the read; a monitoring fee applies (a few cents per 1,000 objects per month); small objects (< 128 KB) are never moved into the IA tier.

**Glacier Instant Retrieval** (easily confused with Standard-IA): millisecond retrieval, but storage is even cheaper than Standard-IA; minimum 90 days. Use case: archived data that occasionally needs an instant read (medical imaging, media assets).

**Storage class decision tree**:

```
Accessed frequently?
├─ Yes → Standard
└─ No ↓
    Access pattern predictable?
    ├─ No → Intelligent-Tiering
    └─ Yes ↓
        Need multi-AZ resilience?
        ├─ No (data is regeneratable) → One Zone-IA
        └─ Yes ↓
            Need immediate access?
            ├─ Yes (instant) ↓
            │   ├─ Rarely accessed → Standard-IA
            │   └─ Archived + occasional instant read → Glacier Instant Retrieval
            └─ No (can wait) ↓
                ├─ A few hours → Glacier Flexible Retrieval
                └─ 12+ hours (cheapest) → Glacier Deep Archive
```

### Lifecycle Rules

**Two action types**: **transition** (move an object between storage classes) and **expiration** (delete an object).

**Transition constraints**: only moves "downward" (toward cheaper); cannot auto-transition from Glacier Deep Archive back to Standard; moving Standard-IA to Glacier requires the object to have sat in IA for at least 30 days.

**Restoring from Glacier**: the `RestoreObject` API temporarily copies a version back into Standard for a number of days you specify; once that period ends, the temporary copy disappears and the original stays in Glacier. **A restore is a temporary copy, not a migration.**

**Five ways lifecycle rules save money** (the last two are often overlooked):

1. ✅ Transition to a cheaper class
2. ✅ Expire old data
3. ✅ Delete old versions (once versioning is enabled)
4. ✅ **Abort incomplete multipart uploads** ⭐ (many people don't know this — tens of GB of dead data can sit there being billed)
5. ✅ Expire delete markers

**A typical policy**:

```
Access log lifecycle:
- Days 0-30:    Standard
- Days 30-90:   Standard-IA
- Days 90-365:  Glacier Flexible Retrieval
- Day 365:      Delete
```

### Versioning ⭐⭐

**Three states**:

| State | Behavior |
|---|---|
| Unversioned (default) | Overwrites replace directly; deletes remove directly |
| Versioning enabled | Every write creates a new version ID; history is retained |
| Versioning suspended | Paused; new objects get version ID "null"; old versions are still kept |

**Mechanics**: every object version has a unique version ID; `GetObject` returns the latest version by default; passing a `versionId` reads a specific version.

**Delete behavior**: in a versioned bucket, `DeleteObject` doesn't actually delete — it places a **delete marker**; the delete marker makes the "latest version" appear absent (GET returns 404); a true delete requires `DeleteObject` with a specific `versionId`; "undeleting" an object is done by removing the delete marker.

**Irreversibility**: once versioning is enabled, it **cannot be turned off entirely — only suspended**; old versions remain even after suspension. State transitions: `Unversioned ──[once enabled]→ Enabled ⇄ Suspended`.

### MFA Delete

**MFA Delete blocks two things**: ✅ permanently deleting a specific object version (a `DeleteObject` with a versionId), ✅ **disabling or changing versioning state** (suspending versioning).

**Characteristics**: **can only be enabled by the bucket owner's root user** (not an IAM admin, not any IAM user/role); **must be enabled via the CLI** (not supported in the console); protects against accidental or malicious deletion.

### Replication

|  | CRR (Cross-Region Replication) | SRR (Same-Region Replication) |
|---|---|---|
| Cross-region | ✅ Yes | ❌ Same region |
| Use case | DR, compliance, lowering read latency | Log aggregation, prod→test sync |

**Replication is asynchronous** — no guarantee of immediate delivery.

**Key points**:

1. **Versioning must be enabled on both sides**
2. **Only objects added after the replication rule is created are replicated** (use S3 Batch Replication for pre-existing objects)
3. Delete replication: **delete markers are not replicated by default** (though "Delete marker replication" can be enabled); **a permanent delete (with a versionId) is never replicated** (protecting the target from ransomware that deletes the source)
4. **Replication does not chain**: for A → B → C, an object replicated from A to B does not continue on to C
5. Cross-account replication is supported (requires an IAM role)

**The replication IAM role**: S3 needs an IAM role to perform replication — its trust policy allows `s3.amazonaws.com`, and its permissions allow reading the source and writing the target.

**Extra requirements for KMS-encrypted objects**: the IAM role also needs KMS Decrypt (source key) + Encrypt (target key) permissions, and "Replicate KMS-encrypted objects" must be explicitly enabled.

## 2. S3 Security

### S3 Access Control Hierarchy

```
1. Block Public Access (strongest — an absolute veto)
   ↓
2. IAM Policy + Bucket Policy evaluation (same account: OR; cross-account: AND)
   ↓
3. Object ACL (legacy, not recommended)
   ↓
4. Bucket ACL (even older)
```

**Precedence**: BPA always wins; any explicit Deny is a veto; with no explicit deny, either side allowing is enough (IAM allow OR bucket policy allow, within the same account).

### Bucket Policy ⭐⭐⭐

**Characteristics**: written as JSON, similar to an IAM policy; **Resource must be explicit** (an IAM policy can omit it; a bucket policy cannot); must include a **Principal** (an IAM policy cannot); can grant cross-account access; capped at 20 KB.

**The two ARN granularities**:

```
arn:aws:s3:::my-bucket          ← bucket level
arn:aws:s3:::my-bucket/*        ← object level
```

| Action | Resource |
|---|---|
| `s3:ListBucket` | `arn:aws:s3:::my-bucket` (bucket level) |
| `s3:GetObject` | `arn:aws:s3:::my-bucket/*` (object level) |
| `s3:PutObject` | `arn:aws:s3:::my-bucket/*` |
| `s3:DeleteObject` | `arn:aws:s3:::my-bucket/*` |

**Trap**: writing `s3:ListBucket` with a `/*` resource never works — `ListBucket` is a bucket-level action.

Correct form:

```json
{
  "Statement": [
    {
      "Action": "s3:ListBucket",
      "Resource": "arn:aws:s3:::my-bucket"
    },
    {
      "Action": ["s3:GetObject", "s3:PutObject"],
      "Resource": "arn:aws:s3:::my-bucket/*"
    }
  ]
}
```

### Common Bucket Policy Conditions

| Condition key | Purpose |
|---|---|
| `aws:SourceIp` | Restrict source IP |
| `aws:SourceVpc` / `aws:SourceVpce` | Allow only from a specific VPC / VPC endpoint |
| `aws:SecureTransport` | Enforce HTTPS (set true) |
| `s3:x-amz-server-side-encryption` | Require encryption on upload (e.g. AES256 or aws:kms) |
| `aws:PrincipalOrgID` | Restrict to AWS Organization members |
| `s3:x-amz-acl` | Control the ACL applied on upload |

### Classic Bucket Policy Templates

**Enforce HTTPS**:

```json
{
  "Effect": "Deny",
  "Principal": "*",
  "Action": "s3:*",
  "Resource": ["arn:aws:s3:::my-bucket", "arn:aws:s3:::my-bucket/*"],
  "Condition": {
    "Bool": { "aws:SecureTransport": "false" }
  }
}
```

**Enforce SSE-KMS uploads**:

```json
{
  "Effect": "Deny",
  "Principal": "*",
  "Action": "s3:PutObject",
  "Resource": "arn:aws:s3:::my-bucket/*",
  "Condition": {
    "StringNotEquals": {
      "s3:x-amz-server-side-encryption": "aws:kms"
    }
  }
}
```

**Enforce a specific KMS key**:

```json
"Condition": {
  "StringNotEquals": {
    "s3:x-amz-server-side-encryption-aws-kms-key-id": "arn:aws:kms:..."
  }
}
```

**Restrict to a specific VPC endpoint**:

```json
{
  "Effect": "Deny",
  "Principal": "*",
  "Action": "s3:*",
  "Resource": "arn:aws:s3:::my-bucket/*",
  "Condition": {
    "StringNotEquals": {
      "aws:SourceVpce": "vpce-12345"
    }
  }
}
```

### Block Public Access (BPA) ⭐⭐⭐

**The four BPA settings**:

| Setting | What it blocks |
|---|---|
| **BlockPublicAcls** | Blocks *new* public ACLs (existing ones unaffected) |
| **IgnorePublicAcls** | Ignores *all* public ACLs, including existing ones |
| **BlockPublicPolicy** | Blocks setting a bucket policy that grants public access |
| **RestrictPublicBuckets** | Restricts access to a public bucket (even a public policy only reaches AWS services and authorized users) |

**Default behavior (post-2023)**: new buckets have **all four BPA settings enabled by default**.

**BPA precedence**: even a bucket policy with `"Principal": "*"` is overridden — public access is still denied when BPA is on. Scope: applies at both the account and bucket level (account level takes precedence).

**What counts as "public"**: `"Principal": "*"`; `"Principal": { "AWS": "*" }`; an ACL granting the `AllUsers` or `AuthenticatedUsers` group.

**Note**: `AuthenticatedUsers` does **not** mean "authenticated users of your account" — it means **any authenticated AWS user, from any AWS account** — which still counts as public.

### The Four SSE Encryption Options ⭐⭐⭐

|  | SSE-S3 | SSE-KMS | SSE-C | CSE |
|---|---|---|---|---|
| Where encryption happens | S3 server-side | S3 server-side | S3 server-side | Client-side |
| Key source | Generated automatically by S3 | A KMS key | Supplied by the customer | Managed by the customer |
| Key storage | Fully managed by AWS | KMS (visible, auditable) | Held by the customer | Held by the customer |
| Request header | `x-amz-server-side-encryption: AES256` | `x-amz-server-side-encryption: aws:kms` | `x-amz-server-side-encryption-customer-key` | None (AWS never sees the encryption) |
| HTTPS required | No | No | **Yes** | Customer's choice |
| Algorithm | AES-256 | AES-256 (via KMS) | AES-256 | Customer's choice |
| Auditability | Not logged | **Logged in CloudTrail** | Not logged | Not logged |
| Cross-account | Automatic | Requires cross-account KMS key config | Requires key sharing | Handled by the customer |
| Extra cost | None | KMS API charges + monthly key fee | None | None |
| Bucket default | ✅ | ✅ | ❌ Not supported | ❌ Not supported |

### SSE-S3

AWS fully manages the key; each object gets its own data key (envelope encryption happens behind the scenes, hidden from you); **S3 has defaulted to SSE-S3 since January 2023** (all new objects encrypted, free of charge); algorithm = AES-256.

### SSE-KMS

**The key trap: dual permission requirement.** To `GetObject` on an encrypted object, you need *both*: ① IAM/bucket policy allowing `s3:GetObject`, and ② **the KMS key policy allowing `kms:Decrypt`** on the key that encrypted it. Configuring only the first still results in a 403!

**When SSE-KMS is required**: ✅ you need to audit who decrypted which object and when (CloudTrail logs KMS decrypt calls), ✅ you need to control key access separately (via the key policy), ✅ sharing encrypted objects cross-account with key-level control, ✅ compliance requires a customer-managed key, ✅ you need control over key rotation.

**The KMS throttling problem (a performance topic)**: KMS API calls have a per-second cap (5,500 – 30,000); a high-throughput S3 application calling KMS on every request will hit the limit. **Fix**: S3 Bucket Keys ⭐

### S3 Bucket Keys (Performance Optimization)

**Mechanism**: S3 uses the KMS key to generate a short-lived, bucket-level key (valid 24 hours), held in S3's memory rather than persisted; every object encryption during that window derives its data key from this bucket key; **KMS calls drop by ~99%.**

**Benefits**: KMS API costs drop ~99%; no more KMS throttling; better performance.

**Enabling**: just check "Bucket Key" in the bucket's settings — **completely free**.

**Judgment call**: "S3 + KMS encryption, hitting KMS throttling" or "S3 + KMS costs too much" → enable S3 Bucket Keys.

### SSE-C

**Characteristics**: the customer sends the key in an HTTP header with every request; S3 uses the supplied key to encrypt/decrypt and **never stores it**; **HTTPS is mandatory** (otherwise the key would travel in plaintext).

**Headers**:

```
x-amz-server-side-encryption-customer-algorithm: AES256
x-amz-server-side-encryption-customer-key: <base64-encoded-key>
x-amz-server-side-encryption-customer-key-MD5: <md5-of-key>
```

**Key limitations**: ❌ **cannot be used from the console** (the console can't pass the key header); ❌ **cannot be set as a bucket default encryption**; must go through the SDK/CLI/API; if the customer loses the key, the data is unrecoverable forever.

### CSE (Client-Side Encryption)

Encryption happens on the client before upload; what reaches S3 is already ciphertext; AWS sees only opaque bytes the whole way through; the customer manages the key; AWS is not involved in encryption at all.

**Implementations**: the AWS Encryption SDK; the S3 Encryption Client (built into some SDKs).

### DSSE-KMS

**Dual-Layer SSE-KMS** (a 2023 addition): two layers of encryption — one client-side, one server-side, each with a different key. Fits compliance scenarios (government, financial) requiring "dual control." More expensive than plain SSE-KMS.

### Bucket Default Encryption

**Supported**: ✅ SSE-S3 (mandatory minimum on all buckets since 2023), ✅ SSE-KMS (with a specified key), ✅ DSSE-KMS. **Not supported**: ❌ SSE-C, ❌ CSE (both are client-side matters the bucket has no part in).

**Rule of thumb**: the three server-side options can all be a default; client-supplied keys (SSE-C / CSE) cannot.

### Pre-signed URLs ⭐⭐⭐

**= A signed S3 URL that lets an unauthorized party temporarily access an S3 object.**

**Core mechanism**:

```python
url = s3.generate_presigned_url(
    'get_object',
    Params={'Bucket': 'my-bucket', 'Key': 'photo.jpg'},
    ExpiresIn=3600  # valid for 1 hour
)
```

**Key traits**: **the URL inherits the permissions of whoever generated it**; can be GET, PUT, DELETE, or POST (not just downloads); has an expiration; the bucket doesn't need to be public — in fact, a private bucket is safer; anyone who gets the URL can use it — the URL itself is the credential.

**Maximum validity, by credential type**:

| Credential type | Max validity |
|---|---|
| IAM user long-term credentials | **7 days** |
| IAM role temporary credentials (assumeRole) | Up to the role session's expiration (36 hours max, usually 1 hour) |
| Instance profile credentials | Up to the IMDS credential's expiration (~6 hours) |

**Trap**: generating a 7-day URL using an EC2 instance profile, whose credentials rotate every ~6 hours — the old URL stops working once the credentials it was signed with rotate out.

### Three Common Uses for Pre-signed URLs

**Use 1: temporary download links**

```python
url = s3.generate_presigned_url(
    'get_object',
    Params={'Bucket': 'ebooks', 'Key': f'user-{user_id}/book.pdf'},
    ExpiresIn=3600
)
```

**Use 2: direct-to-S3 uploads (bypassing the backend)** — the browser asks the backend "I want to upload"; the backend generates a pre-signed PUT URL; the browser PUTs directly to S3, so the data never touches the backend, saving bandwidth and server resources.

**Use 3: temporary sharing with a third party**

### Pre-signed POST (a Variant)

**Difference from pre-signed PUT**: pre-signed PUT sends the data directly to the URL (good for programmatic uploads); pre-signed POST returns a form plus fields, suited to HTML form submission, and **can carry various constraints**.

```python
post_data = s3.generate_presigned_post(
    Bucket='uploads',
    Key='user-${filename}',
    Conditions=[
        ['content-length-range', 0, 10485760],  # max 10 MB
        {'Content-Type': 'image/jpeg'}
    ],
    ExpiresIn=600
)
```

**Typical conditions**: `content-length-range` (file size limit), `Content-Type` (file type restriction), `x-amz-meta-*` (forces specific metadata).

**Judgment call**: "users upload directly, capped at 5 MB, JPEG only" → **Pre-signed POST** (PUT can't impose a size limit); "a simple temporary download link" → a pre-signed GET URL.

### Pre-signed URL Security Considerations

**Risks**: once a URL leaks, anyone can use it until it expires; **an already-issued URL cannot be revoked** (short of deleting the underlying IAM credentials or the object itself).

**Best practices**: keep expirations short (5-15 minutes is common); add IP restrictions; scope each URL to a single key; require HTTPS.

### Object Lambda

S3 Object Lambda lets you attach your own code to S3 GET requests, transforming or processing the data before it's returned to the application.

### Object Lock (Compliance Storage)

**= WORM (Write Once Read Many)** — once written, an object cannot be modified or deleted until a specified time. Use case: compliance auditing (FINRA, SEC, HIPAA).

**Two modes**: **Governance Mode** (users with special permission can override it), **Compliance Mode** (**nobody can override it, including root**, until the retention period ends).

**Legal Hold**: retains indefinitely, until manually removed.

**Prerequisite**: the bucket must have **Versioning enabled**, and **Object Lock must be turned on at bucket creation** — it cannot be added later.

**Judgment call**: legal compliance requiring no root override → **Compliance Mode**; internal company policy → Governance Mode.

### S3 Access Points

**The problem**: a bucket shared by dozens of teams/applications ends up with a bucket policy that's long and unmaintainable.

**The fix**: Access Points give a bucket independent access "front doors," each with its own policy and hostname.

**Benefits**: each access point has its own hostname (`team-a-12345.s3-accesspoint...`); each has its own policy (scoped to a subset of prefixes); different access points can have different VPC restrictions; disabling one doesn't affect the others.

### CORS

**The problem**: a browser loaded from `app.example.com` wants to call `s3.amazonaws.com/my-bucket/file` directly — browsers block cross-origin requests by default.

**The fix**: configure a CORS rule on the bucket.

```json
[{
  "AllowedOrigins": ["https://app.example.com"],
  "AllowedMethods": ["GET", "PUT"],
  "AllowedHeaders": ["*"],
  "ExposeHeaders": ["ETag"],
  "MaxAgeSeconds": 3000
}]
```

**Judgment call**: "frontend JS fails to upload directly to S3, console shows a CORS error" → the bucket has no CORS rule configured.

Field reference: `AllowedOrigin` (domains permitted to make cross-origin requests), `AllowedMethod` (permitted request types: GET/PUT/POST/DELETE/HEAD), `AllowedHeader` (headers allowed in a preflight request), `MaxAgeSeconds` (how long the browser caches a preflight OPTIONS response, cutting down repeat preflights), `ExposeHeader` (response headers client-side JS is allowed to read, e.g. `x-amz-server-side-encryption`).

## 3. S3 Performance + Multipart + Transfer Acceleration

### Performance Basics

**Each bucket prefix has its own request-rate ceiling**:

| Operation | Cap per second (per prefix) |
|---|---|
| GET / HEAD | **5,500 RPS** |
| PUT / POST / DELETE | **3,500 RPS** |

**A prefix** is the portion of an object key before the first `/` (or however it's logically grouped). **S3 shards internally by prefix**, and each prefix gets its own independent 5,500/3,500 RPS.

### Performance Optimization Techniques ⭐⭐⭐

**Technique 1: use multiple prefixes to raise concurrency**

Problem: putting every object under one prefix hits the 5,500 RPS ceiling. Fix: spread objects across multiple prefixes — N prefixes gives roughly N × 5,500 GET RPS, with no hard theoretical ceiling.

**Technique 2: the old "randomize key prefixes" advice is outdated**

The old guidance (pre-2018): "randomize the first few characters of a key, or you'll create hot partitions." Since then, AWS reworked S3's backend architecture in 2018, and **key-prefix randomization is no longer necessary** — keys can follow business-logical naming (year/month/file.jpg). To improve performance now, use multiple distinct prefixes, not randomization.

### Multipart Upload ⭐⭐⭐

**= splitting a large file into parts uploaded in parallel, which S3 then reassembles into one object.**

**Key numbers**:

| Item | Value |
|---|---|
| Max single PUT | 5 GB |
| Threshold requiring multipart | above 5 GB |
| Recommended threshold for multipart | above 100 MB |
| Max object size | **50 TB** (as of Dec 2, 2025; previously 5 TB) |
| Part size | **5 MB – 5 GB** (the final part can be smaller than 5 MB) |
| Max number of parts | **10,000** |

**Mnemonic**: the old "5/5/5/5" rule now updates its third number: 5 MB (min part size), 5 GB (max part size / single PUT), ~~5 TB~~ 50 TB (max object size, as of Dec 2025), 5,500 (GET RPS).

⚠️ Exam question banks may lag behind — if 50 TB isn't among the answer choices, go with 5 TB (the older figure).

**The multipart upload flow**:

```
1. CreateMultipartUpload → returns an UploadId
2. UploadPart × N (can run in parallel) → each part returns an ETag
3. CompleteMultipartUpload → submit the list of part ETags → S3 assembles the object
```

**Three benefits**: ① concurrency — parallel parts multiply throughput; ② resumability — a failed part only needs re-uploading, not the whole file; ③ large-file support — the only way to upload files over 5 GB.

### Stuck (Failed) Multipart Uploads ⭐⭐⭐

**The trap**: once a multipart upload starts, if it's never Completed or Aborted, **the parts already uploaded keep being billed in S3!** You can't see them (they're not objects), but they occupy space and cost money. Left unchecked, this can accumulate GBs to TBs of "ghost storage."

**Fix**: configure a lifecycle rule to abort incomplete multipart uploads:

```yaml
Lifecycle Rule:
  Action: AbortIncompleteMultipartUpload
  After: 7 days
```

**Judgment call**: "S3 bill is unexpectedly high but I don't see that many objects" → incomplete multipart uploads; "how do I clean up failed-upload leftovers" → configure this lifecycle rule.

### Transfer Acceleration ⭐

**= speeds up S3 uploads/downloads using CloudFront's global edge network.**

**How it works**:

```
Without TA:
User (Brazil) → international internet → S3 bucket (US)
                ↑ slow, lossy

With TA:
User (Brazil) → nearest CloudFront edge location (Brazil)
             → AWS's internal backbone → S3 bucket (US)
                ↑ fast, stable
```

**Key point**: the user's request first hits the nearest **CloudFront edge location** (not a region!), then travels over AWS's optimized internal network to S3 — replacing slow, unreliable long-haul public internet.

**Enabling**: turn on Transfer Acceleration in the bucket's properties; once enabled you get a new endpoint: `my-bucket.s3-accelerate.amazonaws.com`.

**Good fit**: ✅ transferring large files across continents, ✅ global applications where users worldwide upload to a central bucket. **Poor fit**: ❌ user and bucket in the same region (pointless), ❌ small files (overhead outweighs the benefit).

**Cost**: TA carries an extra per-GB charge; **if it provides no acceleration, AWS doesn't charge for it.** Use the Speed Comparison Tool to check whether it actually helps.

### Transfer Acceleration vs CloudFront (easily confused)

|  | Transfer Acceleration | CloudFront |
|---|---|---|
| Acceleration direction | **Both upload and download** | Mainly download (caching) |
| Caching | ❌ No caching (every request still reaches S3) | ✅ Caches (served from the edge after the first hit) |
| Fits | Cross-continent transfer to/from S3 | Frequently accessed static content |
| Typical scenario | Large international file uploads | Websites, CDN, video distribution |

**Rule of thumb**: users uploading to a global bucket → **Transfer Acceleration**; users downloading from S3 repeatedly → **CloudFront**.

### S3 Select / Glacier Select

**The problem**: a 1 GB CSV sits in S3, but you only need a few rows — traditionally you'd download the whole file and filter client-side.

**S3 Select's fix**: filter with SQL on the S3 server side, returning only the rows you need.

```sql
SELECT s.name, s.age FROM S3Object s WHERE s.country = 'USA'
```

**Benefits**: less network transfer; less client-side processing; faster. Works with CSV, JSON, and Parquet.

**Glacier Select**: the same SQL-filtering capability applied to data stored in Glacier.

### S3 Byte-Range Fetches

**= downloading only a specific byte range of an object.**

```
GET /large-video.mp4
Range: bytes=0-999999    ← download only the first 1MB
```

**Uses**: ① concurrent downloads — multiple threads each pull a different range, speeding up large downloads; ② partial reads — reading just a file's header (e.g. video metadata); ③ resumable retries — continuing from where a failed download left off.

### Performance Decision Guide

| Scenario | Choice |
|---|---|
| Uploading a large file (> 100 MB) | Multipart Upload |
| Uploading a file > 5 GB | Multipart is required |
| Global users uploading | Multipart + Transfer Acceleration |
| Global users downloading (repeat access) | CloudFront |
| High-RPS applications | Spread across multiple prefixes |
| Reading part of a large file | Byte-Range Fetch |
| Querying structured data | S3 Select |
| KMS encryption + high RPS | S3 Bucket Keys |
