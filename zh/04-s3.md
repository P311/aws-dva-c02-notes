## 一、S3 全貌

### S3 核心概念

**三个核心层级**：AWS 账户 → Bucket（全球唯一名字、绑定 region）→ Object（Key + Value + Metadata + Version ID）

**关键特性**：

| 特性 | 数值 |
|---|---|
| 单个 object 大小 | 0 字节 - **50 TB**（2025-12-02 起从 5 TB 提升） |
| 单次 upload | 最多 **5 GB**，超过要 multipart |
| 推荐 multipart 阈值 | 超过 **100 MB** |
| Bucket 数量限制（每账户） | 默认 100，可申请到 1000 |
| Bucket 名字规则 | 全球唯一、3-63 字符、全小写、不能含下划线 |
| Object key 长度 | 最多 1024 字节 |
| Object 数量 | 无限 |
| 持久性 | **11 个 9**（99.999999999%） |
| 可用性 | 4 个 9（Standard） |

> ⚠️ 50 TB 是 2025 年底才生效的新上限，考试题库可能还停留在 5 TB。真实场景以官方文档为准。

**Bucket 命名规则**：3-63 字符；全小写字母、数字、连字符（-）、点（.）；不能有下划线（`_`）；不能有大写字母；不能以连字符开头/结尾；不能像 IP 地址；不能以 `xn--` 开头。

**关键概念**：Bucket 名字**全球唯一**；Bucket 是 **region 级**资源，object 物理上存在那个 region 的多个 AZ；没有"目录"概念——Object key 是 flat 字符串；Object 不可修改——只能整个覆盖。

**11 个 9 持久性**：存 1000 万个 object，预期每 1 万年丢失 1 个。

### Storage Classes ⭐⭐⭐

| Class | 用途 | 存储成本 | 检索成本 | 检索时间 | 最少存储期 | 跨 AZ |
|---|---|---|---|---|---|---|
| **Standard** | 频繁访问 | 标准 | 无 | 即时 | 无 | ✅ 多 AZ |
| **Standard-IA** | 不常访问，需要时即时读 | 便宜 | 有 retrieval 费 | 即时 | 30 天 | ✅ 多 AZ |
| **One Zone-IA** | 不常访问 + 可重生数据 | 更便宜 | 有 retrieval 费 | 即时 | 30 天 | ❌ 单 AZ |
| **Intelligent-Tiering** | 访问模式不可预测 | 智能调整 | 无 | 即时 | 无 | ✅ 多 AZ |
| **Glacier Instant Retrieval** | 归档 + 偶尔即时读 | 很便宜 | 有 | 即时 | 90 天 | ✅ 多 AZ |
| **Glacier Flexible Retrieval** | 归档 + 不急用 | 更便宜 | 有 | 分钟到小时 | 90 天 | ✅ 多 AZ |
| **Glacier Deep Archive** | 长期归档 | **最便宜** | 有 | 12 小时起 | 180 天 | ✅ 多 AZ |

**Glacier 三种 retrieval 模式**：

- **Glacier Flexible Retrieval**：Expedited（1-5 分钟，最贵）、Standard（3-5 小时，默认）、Bulk（5-12 小时，最便宜）
- **Glacier Deep Archive**：Standard（12 小时）、Bulk（48 小时）

**One Zone-IA 适用场景**：✅ 转码后的视频缩略图（原始视频在 Standard，丢了能再生成）、✅ 缓存的 ML 推理结果、✅ 第二份备份；❌ 用户上传的唯一原始照片、❌ 合规审计日志。

**Intelligent-Tiering 关键点**：**没有 retrieval fee**（无论从哪一层读）；收 monitoring fee（每 1000 个 object 几分钱/月）；小对象（< 128 KB）不会被移动到 IA tier。

**Glacier Instant Retrieval**（易混）：毫秒级取回，但存储更便宜（比 Standard-IA 还低），最少 90 天。场景：归档但偶尔需要立刻读（医疗影像、媒体素材）。

**Storage Class 选择决策树**：

```
访问频率高?
├─ 是 → Standard
└─ 否 ↓
    访问模式可预测?
    ├─ 否 → Intelligent-Tiering
    └─ 是 ↓
        AZ 容灾要求高?
        ├─ 否(数据可重生)→ One Zone-IA
        └─ 是 ↓
            需要立即访问?
            ├─ 是(即时)↓
            │   ├─ 不常用 → Standard-IA
            │   └─ 归档 + 偶尔即时 → Glacier Instant Retrieval
            └─ 否(可等待)↓
                ├─ 几小时 → Glacier Flexible Retrieval
                └─ 12+ 小时(最便宜)→ Glacier Deep Archive
```

### Lifecycle Rules

**两种动作**：**Transition action**（把 object 从一个 storage class 移到另一个）、**Expiration action**（把 object 删除）。

**Transition 规则的限制**：只能"向下"转（更便宜的方向）；不能从 Glacier Deep Archive 自动 transition 回 Standard；Standard-IA 转 Glacier 至少要在 IA 里待 30 天。

**Restore from Glacier**：`RestoreObject` API → 临时复制一份回 Standard，你指定几天；时间到了，复制的版本消失，原 object 还在 Glacier。**Restore 不是迁移，是临时复制**。

**Lifecycle 省钱场景**（共 5 个，常被忽略）：

1. ✅ Transition 到便宜的 class
2. ✅ Expiration 删除老数据
3. ✅ 删除老版本（versioning 启用后）
4. ✅ **删除 incomplete multipart upload** ⭐（很多人不知道，几十 GB 废数据躺着收费）
5. ✅ Expire delete markers

**典型场景**：

```
访问日志生命周期:
- 0-30 天:    Standard
- 30-90 天:   Standard-IA
- 90-365 天:  Glacier Flexible Retrieval
- 365 天:     删除
```

### Versioning ⭐⭐

**三种状态**：

| 状态 | 行为 |
|---|---|
| Unversioned（默认） | 覆盖直接覆盖，删除直接删 |
| Versioning enabled | 每次写都生成新 version ID，保留历史 |
| Versioning suspended | 暂停，新对象 version ID = "null"，老版本仍保留 |

**关键机制**：每个 object 版本有唯一 version ID；GetObject 默认返回最新版本；加 versionId 参数可读特定版本。

**删除的特殊行为**：在 versioning bucket 里 `DeleteObject` 不真的删除，而是放一个 **delete marker**；delete marker 让"最新版本"看起来不存在（GET 返回 404）；真正删除：用 `DeleteObject` + 指定 versionId；恢复"被删除"的对象：**删掉 delete marker** 即可。

**不可逆**：一旦启用 versioning，**不能彻底关闭，只能 Suspend**；Suspend 后老版本依然保留。状态转换：`Unversioned ──[一旦启用]→ Enabled ⇄ Suspended`。

### MFA Delete

**MFA Delete 能阻止两件事**：✅ 永久删除某个 object 版本（带 versionId 的 DeleteObject）；✅ **关闭 / 修改 versioning 状态**（Suspend versioning）。

**特点**：**只能由 bucket owner 的 root user 启用**（不是 IAM admin、不是任何 IAM user/role）；**必须用 CLI 启用**（控制台不支持）；防止误删/恶意删除。

### Replication（复制）

|  | CRR (Cross-Region Replication) | SRR (Same-Region Replication) |
|---|---|---|
| 跨 region | ✅ 是 | ❌ 同一个 region |
| 用途 | DR、合规、降低读延迟 | 日志聚合、生产→测试同步 |

**复制是异步的**（不保证立刻到）。

**关键点**：

1. **必须两边都启用 versioning**
2. **只复制启用复制规则之后新增的 object**（已有 object 用 S3 Batch Replication）
3. 删除是否复制：**默认 delete marker 不复制**，可以配置 "Delete marker replication"；**永久删除（带 versionId）永远不复制**（防勒索病毒删了源也删目标）
4. **不会链式复制**：A → B → C 时，A 复制到 B 的 object 不会继续复制到 C
5. 跨账户复制也支持（要配 IAM role）

**复制的 IAM Role**：S3 需要一个 IAM role 来执行复制。trust policy 允许 `s3.amazonaws.com`，permissions 允许读源 + 写目标。

**KMS 加密对象复制额外要求**：IAM role 还要有 KMS Decrypt（源 key）+ Encrypt（目标 key）权限；必须显式启用 "Replicate KMS-encrypted objects"。

## 二、S3 Security

### S3 访问控制层级（优先级）

```
1. Block Public Access(最强,"一票否决")
   ↓
2. IAM Policy + Bucket Policy 评估(同账户:OR;跨账户:AND)
   ↓
3. Object ACL(老式,不推荐)
   ↓
4. Bucket ACL(更老)
```

**优先级原则**：BPA 永远优先；任何 explicit Deny 一票否决；没有 explicit deny 时，任一允许即可（IAM allow OR bucket policy allow，同账户内）。

### Bucket Policy ⭐⭐⭐

**特点**：用 JSON 写，类似 IAM policy；必须**显式写 Resource**（IAM policy 可省，bucket policy 必须写）；必须有 **Principal**（IAM policy 不能有 Principal）；可以授权跨账户访问；大小限制 20 KB。

**Resource ARN 的两种粒度**：

```
arn:aws:s3:::my-bucket          ← bucket 级别
arn:aws:s3:::my-bucket/*        ← object 级别
```

| Action | Resource |
|---|---|
| `s3:ListBucket` | `arn:aws:s3:::my-bucket`（bucket 级） |
| `s3:GetObject` | `arn:aws:s3:::my-bucket/*`（object 级） |
| `s3:PutObject` | `arn:aws:s3:::my-bucket/*` |
| `s3:DeleteObject` | `arn:aws:s3:::my-bucket/*` |

**陷阱**：`s3:ListBucket` 用 `/*` 写法永远不生效（ListBucket 是 bucket 级 action）。

正确写法：

```json
{
  "Statement": [
    {
      "Action": "s3:ListBucket",
      "Resource": "arn:aws:s3:::my-bucket"
    },
    {
      "Action": ["s3:GetObject", "s3:PutObject"],
      "Resource": "arn:aws:s3:::my-bucket/*"
    }
  ]
}
```

### Bucket Policy 常用 Conditions

| Condition Key | 用途 |
|---|---|
| `aws:SourceIp` | 限制访问来源 IP |
| `aws:SourceVpc` / `aws:SourceVpce` | 只允许来自特定 VPC / VPC Endpoint |
| `aws:SecureTransport` | 强制 HTTPS（设 true） |
| `s3:x-amz-server-side-encryption` | 强制上传加密（如 AES256 或 aws:kms） |
| `aws:PrincipalOrgID` | 限制 AWS Organization 成员 |
| `s3:x-amz-acl` | 控制上传时的 ACL |

### 经典 Bucket Policy 模板

**强制 HTTPS**：

```json
{
  "Effect": "Deny",
  "Principal": "*",
  "Action": "s3:*",
  "Resource": ["arn:aws:s3:::my-bucket", "arn:aws:s3:::my-bucket/*"],
  "Condition": {
    "Bool": { "aws:SecureTransport": "false" }
  }
}
```

**强制 SSE-KMS 上传**：

```json
{
  "Effect": "Deny",
  "Principal": "*",
  "Action": "s3:PutObject",
  "Resource": "arn:aws:s3:::my-bucket/*",
  "Condition": {
    "StringNotEquals": {
      "s3:x-amz-server-side-encryption": "aws:kms"
    }
  }
}
```

**强制特定 KMS Key**：

```json
"Condition": {
  "StringNotEquals": {
    "s3:x-amz-server-side-encryption-aws-kms-key-id": "arn:aws:kms:..."
  }
}
```

**限制特定 VPC Endpoint**：

```json
{
  "Effect": "Deny",
  "Principal": "*",
  "Action": "s3:*",
  "Resource": "arn:aws:s3:::my-bucket/*",
  "Condition": {
    "StringNotEquals": {
      "aws:SourceVpce": "vpce-12345"
    }
  }
}
```

### Block Public Access (BPA) ⭐⭐⭐

**4 个 BPA 设置**：

| 设置 | 阻止什么 |
|---|---|
| **BlockPublicAcls** | 阻止新增 public ACL（已有的不影响） |
| **IgnorePublicAcls** | 忽略所有 public ACL（已有的也作废） |
| **BlockPublicPolicy** | 阻止设置含 public 的 bucket policy |
| **RestrictPublicBuckets** | 限制 public bucket 的访问（即使 policy 是 public，也只允许 AWS 服务和授权用户） |

**默认行为（2023 年后）**：AWS 新建 bucket **默认全部启用 BPA**（4 个全开）。

**BPA 优先级**：即使 bucket policy 写了 `"Principal": "*"`，BPA 启用 → public 访问仍被拒。作用范围：账户级 + bucket 级（账户级 > bucket 级）。

**"Public" 的判定**：`"Principal": "*"`；`"Principal": { "AWS": "*" }`；ACL 包含 `AllUsers` 或 `AuthenticatedUsers` 组。

**注意**：`AuthenticatedUsers` ≠ "你账户的认证用户"！它指**任何 AWS 用户**（任何 AWS 账户的人都能访问），所以也是 public。

### SSE 加密四种对比 ⭐⭐⭐

|  | SSE-S3 | SSE-KMS | SSE-C | CSE |
|---|---|---|---|---|
| 加密位置 | S3 服务端 | S3 服务端 | S3 服务端 | 客户端 |
| 密钥来源 | S3 自动生成 | KMS Key | 客户提供 | 客户管理 |
| 密钥存储 | AWS 完全管 | KMS（可见、可审计） | 客户自存 | 客户自存 |
| 请求 Header | `x-amz-server-side-encryption: AES256` | `x-amz-server-side-encryption: aws:kms` | `x-amz-server-side-encryption-customer-key` | 无（AWS 看不到加密） |
| HTTPS 必需 | 否 | 否 | **必需** | 客户决定 |
| 加密算法 | AES-256 | AES-256（KMS） | AES-256 | 客户选 |
| 审计 | 不记录 | **CloudTrail 记录** | 不记录 | 不记录 |
| 跨账户 | 自动 | 需要 KMS key 跨账户配置 | 需要 key 共享 | 客户处理 |
| 额外费用 | 无 | KMS API 费 + key 月费 | 无 | 无 |
| Bucket Default | ✅ | ✅ | ❌ 不能 | ❌ 不能 |

### SSE-S3

AWS 完全管理 key；每个 object 用独立 data key（背后是 envelope encryption，AWS 隐藏）；**2023 年 1 月起 S3 默认开启 SSE-S3**（所有新 object 都加密，免费）；算法 = AES-256。

### SSE-KMS

**关键点：双重权限要求**。要 GetObject 加密 object，必须同时：① IAM/bucket policy 允许 `s3:GetObject`；② **KMS Key Policy 允许 `kms:Decrypt`**（针对加密用的 key）。只配第一个 → 依然 403！

**SSE-KMS 必需的场景**：✅ 需要审计谁、什么时候解密了哪个 object（CloudTrail 记录 KMS 解密）；✅ 需要控制 key 访问权限（用 KMS key policy）；✅ 跨账户共享加密 object + 控制 key 权限；✅ 合规要求用客户管理的 key；✅ 需要 key 轮换控制。

**KMS API 限流问题（性能考点）**：KMS 每秒 API 调用有上限（5,500 - 30,000）；高吞吐 S3 应用每次请求都调 KMS → 撞限流。**解决方案**：S3 Bucket Keys ⭐

### S3 Bucket Keys（性能优化）

**机制**：S3 用 KMS key 生成一个短期 bucket-level key（24 小时有效）；这个 bucket key 在 S3 内存里，不存盘；期间所有 object 加密用这个 bucket key 派生 data key；**KMS 调用减少 99%**。

**好处**：KMS API 费用降 99%；不再撞 KMS 限流；性能提升。

**启用**：bucket 设置里勾选 "Bucket Key" 即可，**完全免费**。

**判断**："S3 + KMS 加密，KMS 限流" 或 "S3 + KMS 成本太高" → 启用 S3 Bucket Keys。

### SSE-C

**特点**：客户每次请求都把 key 放在 HTTP header 里传给 S3；S3 用客户提供的 key 加密/解密，**不存 key**；**HTTPS 必需**（否则 key 明文在网上传）。

**Header**：

```
x-amz-server-side-encryption-customer-algorithm: AES256
x-amz-server-side-encryption-customer-key: <base64-encoded-key>
x-amz-server-side-encryption-customer-key-MD5: <md5-of-key>
```

**关键限制**：❌ **不能在控制台用 SSE-C**（控制台不支持传 key header）；❌ **不能设为 bucket default encryption**；必须用 SDK / CLI / API；客户自己丢了 key → 数据永远解不开。

### CSE (Client-Side Encryption)

加密在客户端发生；上传到 S3 的已经是密文；AWS 全程看到的都是乱码；客户管 key；AWS 完全不参与加密。

**实现**：AWS Encryption SDK；S3 Encryption Client（部分 SDK 内置）。

### DSSE-KMS

**Dual-Layer SSE-KMS**（2023 年新选项）：两层加密——第一层在客户端，第二层在服务端用不同 key；合规场景：政府、金融的"双重控制"要求；比 SSE-KMS 贵。

### Bucket Default Encryption

**支持**：✅ SSE-S3（2023 年起所有 bucket 强制至少这个）；✅ SSE-KMS（指定 key）；✅ DSSE-KMS；❌ SSE-C（不支持作为默认）；❌ CSE（客户端事，bucket 不参与）。

**记忆**：服务端加密的三种 → 都能作 default；客户端 key（SSE-C / CSE）→ 不能作 default。

### Pre-signed URL ⭐⭐⭐

**= 带签名的 S3 URL，让未授权的人也能临时访问 S3 object**

**核心机制**：

```python
url = s3.generate_presigned_url(
    'get_object',
    Params={'Bucket': 'my-bucket', 'Key': 'photo.jpg'},
    ExpiresIn=3600  # 1 小时有效
)
```

**关键特性**：**URL 继承生成者的权限**；可以是 GET、PUT、DELETE、POST（不只是下载）；有过期时间；不需要 S3 是 public——其实 bucket 是 private 的更安全；任何人拿到 URL 都能用——URL 本身就是凭证。

**最长有效期**：

| 凭证类型 | 最长有效期 |
|---|---|
| IAM User 长期凭证 | **7 天** |
| IAM Role 临时凭证（assumeRole） | 最多到 role session 过期（实际上限 36 小时，通常 1 小时） |
| Instance Profile 凭证 | 最多到 IMDS 凭证过期（约 6 小时） |

**陷阱**：你用 EC2 instance profile 生成 7 天 URL，但凭证 6 小时后轮换 → 新凭证下旧 URL 失效。

### Pre-signed URL 三大典型用途

**用途 1：临时下载链接**

```python
url = s3.generate_presigned_url(
    'get_object',
    Params={'Bucket': 'ebooks', 'Key': f'user-{user_id}/book.pdf'},
    ExpiresIn=3600
)
```

**用途 2：用户直传 S3（前端绕过后端）**——浏览器请求后端"我要上传"；后端生成 pre-signed PUT URL；浏览器直接 PUT 到 S3（数据不经过后端）；节省后端带宽和服务器资源。

**用途 3：临时分享给第三方**

### Pre-signed POST（变体）

**和 Pre-signed PUT 的区别**：Pre-signed PUT 直接 PUT 到 URL（适合编程式上传）；Pre-signed POST 返回表单 + 字段，适合 HTML 表单提交，**带各种限制条件**。

```python
post_data = s3.generate_presigned_post(
    Bucket='uploads',
    Key='user-${filename}',
    Conditions=[
        ['content-length-range', 0, 10485760],  # 最大 10 MB
        {'Content-Type': 'image/jpeg'}
    ],
    ExpiresIn=600
)
```

**典型 conditions**：`content-length-range`（限制文件大小）、`Content-Type`（限制文件类型）、`x-amz-meta-*`（强制特定 metadata）。

**判断**："用户直传 + 限制 5MB 以内 + 只能 jpeg" → **Pre-signed POST**（PUT 不能加大小限制）；"简单临时下载链接" → Pre-signed GET URL。

### Pre-signed URL 安全考量

**风险**：URL 一旦泄露，任何人都能用（在过期前）；**不能撤销已生成的 URL**（除非删除 IAM 凭证或 object）。

**最佳实践**：过期时间尽量短（常用 5-15 分钟）；加 IP 限制；每个 URL 只对应一个 key；HTTPS 必需。

### Object Lambda

S3 Object Lambda 允许你在 S3 GET 请求上挂自己的代码，在数据返回给应用之前做修改和处理。

### Object Lock（合规存储）

**= WORM (Write Once Read Many)** — 一旦写入不能修改、不能删除，直到指定时间。用途：合规审计（FINRA、SEC、HIPAA）。

**两种模式**：**Governance Mode**（有特殊权限的人能 override）、**Compliance Mode**（**任何人都不能 override，包括 root！**，直到保留期到）。

**Legal Hold**：无限期保留（直到手动移除）。

**前提**：bucket 必须**启用 Versioning**，且**创建时启用 Object Lock**（事后不能加）。

**判断**：法律合规、防 root override → **Compliance Mode**；公司内部规定 → Governance Mode。

### S3 Access Points

**问题**：一个 bucket 被几十个团队/应用共用，bucket policy 写起来超长难维护。

**解决**：Access Points = bucket 的"独立访问入口"，每个有自己的 policy 和 hostname。

**好处**：每个 access point 有独立 hostname（`team-a-12345.s3-accesspoint...`）；每个 access point 有独立 policy（只针对一部分前缀）；可以为不同 access point 配不同 VPC 限制；可以禁用某个不影响其他。

### CORS

**问题**：浏览器从 `app.example.com` 加载，想直接请求 `s3.amazonaws.com/my-bucket/file` → 浏览器默认拦截跨域请求。

**解决**：bucket 配置 CORS rule。

```json
[{
  "AllowedOrigins": ["https://app.example.com"],
  "AllowedMethods": ["GET", "PUT"],
  "AllowedHeaders": ["*"],
  "ExposeHeaders": ["ETag"],
  "MaxAgeSeconds": 3000
}]
```

**判断**："前端 JS 直传 S3 失败，控制台报 CORS 错误" → bucket 没配 CORS rule。

字段说明：`AllowedOrigin`（允许发起跨域请求的域名）、`AllowedMethod`（允许的请求方法：GET/PUT/POST/DELETE/HEAD）、`AllowedHeader`（preflight 请求允许的 header）、`MaxAgeSeconds`（浏览器缓存 preflight OPTIONS 响应的秒数，减少重复 preflight）、`ExposeHeader`（客户端 JS 能访问到的响应 header，如 `x-amz-server-side-encryption`）。

## 三、S3 Performance + Multipart + Transfer Acceleration

### S3 性能基础

**每个 bucket 的 prefix 有独立的请求速率上限**：

| 操作 | 每秒上限（每 prefix） |
|---|---|
| GET / HEAD | **5,500 RPS** |
| PUT / POST / DELETE | **3,500 RPS** |

**Prefix（前缀）** = object key 中第一个 `/` 之前的部分（或逻辑分组）。**S3 内部按 prefix 做 sharding**，每个 prefix 独立 5500/3500 RPS。

### 性能优化技巧 ⭐⭐⭐

**技巧 1：用多个 prefix 提升并发**

问题：所有 object 用同一个 prefix → 撞 5500 RPS 上限。优化：分散到多个 prefix，N 个 prefix = N × 5500 GET RPS，无理论上限。

**技巧 2：旧的"key 名前缀随机化"已过时**

老说法（2018 年前）："key 前几个字符要 random，否则会 hot partition"。现在：AWS 在 2018 年改进了 S3 后端架构，**不再需要 key 前缀随机化**，key 可以按业务逻辑命名（year/month/file.jpg）。想提升性能 → 用多个不同 prefix，不是随机化。

### Multipart Upload ⭐⭐⭐

**= 把大文件拆成多个 part 并行上传，再让 S3 合并成一个 object**

**关键数字**：

| 项目 | 值 |
|---|---|
| 单次 PUT 最大 | 5 GB |
| 必须用 multipart 的阈值 | 超过 5 GB |
| 推荐使用 multipart 的阈值 | 超过 100 MB |
| 单个 object 最大 | **50 TB**（2025-12-02 起，旧值 5 TB） |
| 每个 part 大小 | **5 MB - 5 GB**（最后一个 part 可以 < 5 MB） |
| 最大 part 数 | **10,000** |

**记忆口诀**："5 / 5 / 5 / 5"（老版本）→ 现在单 object 最大已升为 **50 TB**：5 MB（最小 part）、5 GB（最大 part / 单次 PUT）、~~5 TB~~ 50 TB（单 object 最大，2025-12 起）、5,500（GET RPS）。

⚠️ DVA 题库可能滞后。如果选项里没 50 TB，选 5 TB（老题）。

**Multipart Upload 流程**：

```
1. CreateMultipartUpload → 返回 UploadId
2. UploadPart × N(可并行)→ 每个 part 返回 ETag
3. CompleteMultipartUpload → 提交所有 part 的 ETag 列表 → S3 合并
```

**三大好处**：① 并发——多 part 并行，吞吐量倍增；② 可恢复——单 part 失败，重传那个 part 即可；③ 大文件支持——唯一能上传 > 5 GB 文件的方式。

### 失败的 Multipart Upload "卡住" ⭐⭐⭐

**陷阱**：multipart upload 启动后，如果没 Complete 也没 Abort，**已上传的 part 依然在 S3 里收费**！你看不到这些 part（不是 object），但它们占空间、收费。长期累积可能产生几 GB 到几 TB 的"幽灵存储"。

**解决方案**：Lifecycle Rule 配置 incomplete multipart upload expiration：

```yaml
Lifecycle Rule:
  Action: AbortIncompleteMultipartUpload
  After: 7 days
```

**判断**："S3 账单异常高，但看不到这么多 object" → incomplete multipart upload；"如何清理上传失败的临时数据" → Lifecycle 配置。

### Transfer Acceleration ⭐

**= 利用 CloudFront 的全球边缘网络加速 S3 上传/下载**

**工作原理**：

```
没有 TA:
用户(巴西)→ 跨国互联网 → S3 bucket(美国)
                ↑ 慢、丢包

启用 TA:
用户(巴西)→ 最近的 CloudFront 边缘点(巴西)
            → AWS 内部专线 → S3 bucket(美国)
                ↑ 快、稳定
```

**关键点**：用户请求先到最近的 **CloudFront 边缘点**（不是 region！），然后通过 AWS 优化的内部网络到 S3；替代慢且不稳定的公网长距离传输。

**启用方法**：在 bucket 属性里启用 Transfer Acceleration；启用后获得新 endpoint：`my-bucket.s3-accelerate.amazonaws.com`。

**适用场景**：✅ 跨大洲传输大文件、✅ 国际化应用，全球用户上传到中心 bucket；❌ 用户和 bucket 在同 region（没意义）、❌ 小文件（开销大于收益）。

**费用**：TA 额外收费（按 GB）；如果没加速效果，**AWS 不收 TA 费用**！用 Speed Comparison Tool 测试是否有加速。

### Transfer Acceleration vs CloudFront（易混考点）

|  | Transfer Acceleration | CloudFront |
|---|---|---|
| 加速方向 | **上传 + 下载都加速** | 主要下载（缓存） |
| 是否缓存 | ❌ 不缓存（每次都到 S3） | ✅ 缓存（首次后从边缘读） |
| 适合 | 跨国传输到/从 S3 | 高频访问的静态内容 |
| 典型场景 | 跨国大文件上传 | 网站、CDN、视频分发 |

**记忆**：用户上传到全球 bucket → **Transfer Acceleration**；用户从 S3 下载 + 重复访问 → **CloudFront**。

### S3 Select / Glacier Select

**问题**：S3 上有 1 GB CSV 文件，只想读其中几行 → 传统做法整个文件下载下来再筛选。

**S3 Select 解决方案**：用 SQL 在 S3 服务端过滤，只返回需要的几行。

```sql
SELECT s.name, s.age FROM S3Object s WHERE s.country = 'USA'
```

**好处**：减少网络传输；节省客户端处理资源；更快。适合 CSV、JSON、Parquet 格式的数据筛选。

**Glacier Select**：对 Glacier 里的数据做 SQL 过滤。

### S3 Byte-Range Fetches

**= 只下载 object 的特定字节范围**

```
GET /large-video.mp4
Range: bytes=0-999999    ← 只下前 1MB
```

**用途**：① 并发下载——多线程各下一段，加速大文件下载；② 部分读取——只读文件头（如视频元数据）；③ 重试机制——失败后从断点继续。

### 性能优化决策图

| 场景 | 选择 |
|---|---|
| 上传大文件（> 100 MB） | Multipart Upload |
| 上传 > 5 GB 文件 | 必须 Multipart |
| 全球用户上传 | Multipart + Transfer Acceleration |
| 全球用户下载（重复访问） | CloudFront |
| 高 RPS 应用 | 多 prefix 分散 |
| 读取大文件部分内容 | Byte-Range Fetch |
| 查询结构化数据 | S3 Select |
| KMS 加密 + 高 RPS | S3 Bucket Keys |
